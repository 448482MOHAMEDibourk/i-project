# معايير المشروع (STANDARDS)

هذا الملف يَجمَع القواعد العامة والمنهجية المطبّقة في مستودع `i-project` ويحوّلها إلى مرجع عملي موجز يُستخدم للحكم على التصميم، التنفيذ، والاختبار. يعتمد الملف مبدأ "التعلّم قبل التجريب" ويستند إلى محتويات المستودع الحالية (`docs/history.md`, `data/clean/*`, `requirements.txt`, `src/`, `scripts/`, `.github/workflows/`).

ملاحظة سريعة: هذا الملف هو دليل مرجعي للإنسان والوكيل المحلي. أي تعديل جوهري على القواعد يُسجَّل في `docs/history.md` وفقًا لقواعدنا (R3 / M1).

---

## 1. الملخّص السريع للقواعد (موجز)

- **R1 / M1 — أولوية التخطيط (Planning Primacy):** ثبّت القواعد والهيكل والتوثيق قبل أي scaffolding.
- **R3 — التوثيق الفوري:** سجّل قرارات التصميم والتغييرات المهمة فورًا في `docs/history.md`.
- **G10 / M4 — التوحيد والتنظيف:** السكريبتات في `scripts/`، التوثيق في `docs/`، الكود في `src/`، النماذج في `models/`.
- **G4 — عدم رفع البيانات الضخمة:** أضف `models/` إلى `.gitignore`؛ لا تُدفع ملفات GGUF إلى Git.
- **R2 / R4 — بيئة قابلة للتكرار وفصل التبعية:** ثبّت الإصدارات في `requirements.txt` واحتفظ بالمتغيرات في ملفات `.env` أو `paths.yaml`.
- **M3 — إلزامية الاختبار المباشر:** كل ملف أساسي يُغطَّى فورًا بمسار CI (smoke)؛ راجع `.github/workflows/ci-smoke-ai-school.yml`.
- **M3 — إلزامية الاختبار المباشر:** كل ملف أساسي يُغطَّى فورًا بمسار CI (smoke)؛ راجع `.github/workflows/ci-smoke-ai-school.yml`.
- **M6 — إلزامية التحقق السياقي من التبعيات (Contextual Dependency Verification Mandate):** قبل دمج أو تحديث أي تبعية (مكتبة أو نموذج أو أداة بنى تحتية)، تطابق التغيير مع الوثائق ذات الصلة (`docs/history.md`, `docs/STANDARDS.md`) وتحقق من توافقه مع **M2**. يجب توثيق قرار القبول أو الرفض في `docs/history.md` كخطوة إلزامية.
- **G7 — نقطة إطلاق واحدة:** شغّل البيئة عبر أمرٍ واحدٍ واضحٍ (مثلاً `docker compose up -d`).

## 2. تطبيق القواعد عمليًا على بنية المستودع

- `src/` — الكود الأساسي: دروس، وحدات تنفيذية. مثال: `src/lessons/lesson_01.py`.
- `scripts/` — جميع السكريبتات المساعدة وتشغيل الاختبارات: مثال: `scripts/run_smoke.sh`, `scripts/apply_history_patch.sh`.
- `docs/` — التوثيق والقرار: `docs/history.md`, `docs/STANDARDS.md`, وملفات السياسات.
- `models/` — مكان تخزين النماذج المحلية (غير مُدخلة في Git). ضع `models/` في `.gitignore`.
- `.github/workflows/ci-smoke-ai-school.yml` — مسار الـ CI المكلف بتطبيق M3 (smoke tests على `src/lessons/`).

---

## 3. قائمة تحقق تنفيذية (Checklist)

لتطبيق القواعد أثناء تغييرات المشروع، اتبع هذه القائمة:

1. قبل أي تغيير هيكلي كبير: تحديث `docs/history.md` (R1/R3).
2. تأكد من أن أي سكريبت جديد يوضع في `scripts/` وتُحدَّد صلاحيات التنفيذ (chmod +x) قبل الالتزام.
3. أضف `models/` إلى `.gitignore` إن لم يكن موجودًا: `echo "models/" >> .gitignore`.
4. حدّث `requirements.txt` مع نسخ ثابتة لكل تبعية جديدة (R4).
5. أضف أو عدّل ملف CI (في `.github/workflows/`) ليشمل اختبار smoke الذي يركّب المتطلبات، ويشغّل `scripts/run_smoke.sh` (M3).
6. اختبر محليًا قبل رفع التغيير: شغّل `scripts/run_smoke.sh` داخل حاوية التطوير أو venv.

## 4. أوامر مفيدة/أمثلة للتشغيل

ملاحظة: شغّل هذه الأوامر من جذر المستودع.

- تثبيت التبعيات محليًا:

```bash
python -m pip install --upgrade pip
pip install --no-cache-dir -r requirements.txt
```

- تشغيل دروس smoke محليًا (مكرر لما في CI):

```bash
bash scripts/run_smoke.sh
```

- بدء البيئة عبر Docker Compose (موحدة):

```bash
docker compose up -d
```

- إضافة `models/` إلى `.gitignore`:

```bash
grep -qxF "models/" .gitignore || echo "models/" >> .gitignore
```

## 5. أمان والتزام

- لا ترفع ملفات نماذج كبيرة أو أوزان (GGUF) إلى Git. بدلاً من ذلك، وفر سكريبت `scripts/fetch_models.sh` أو توثيقًا يعرض كيفية تنزيل الملفات إلى `models/` محليًا.
- احتفظ بالمفاتيح والمتغيرات السرية خارج Git في ملفات `.env` أو بواسطة أسرار GitHub Actions.

## 6. تنسيق الكود وإدارة التبعيات (Code Formatting & Dependency Management)

لتقليل الخلافات في التنسيق ولمنع تغيّرات مفاجِئة في السلوك عند تحديث الحزم، اتبع القواعد التالية:

- **قاعدة تنسيق الكود (Code Formatting):**
  - الوصف: الالتزام بتنسيق موحّد للمشروع لتقليل مراجعات الـ style والأخطاء البسيطة.
  - الأدوات الموصى بها: `black` (formatter)، `ruff` (linter/formatter سريع)، و`pre-commit` لتشغيلهما قبل كل `commit`.
  - الملفات/الإعدادات المقترحة: أضف `pyproject.toml` مع إعدادات `black` و`ruff`، وملف `.pre-commit-config.yaml` يُفعّل hooks الأساسية.
  - أوامر فحص سريعة:

```bash
python -m pip install --upgrade pip
pip install --no-cache-dir black ruff pre-commit
pre-commit run --all-files
```

- **قاعدة إدارة التبعيات (Dependency Management):**
  - الوصف: قُم بتثبيت وإدارة تبعيات المشروع بطريقة قابلة للتكرار، وحدد نسخ الحزم في `requirements.txt`.
  - الأدوات الموصى بها: `pip-tools` (`pip-compile`/`pip-sync`) لإدارة ملف `requirements.in` و`requirements.txt` بدقة، و`Dependabot` لتحديثات آلية عبر GitHub.
  - إعدادات مقترحة:
    - الحفاظ على `requirements.txt` في الجذر مع نسخ مقيدة.
    - إضافة `.github/dependabot.yml` لطلب تحديثات تلقائية مقنّنة.
  - سبب الفائدة: يمنع تحديثات مفاجِئة تُسبّب فشل CI أو تغيّر سلوكاً غير مرغوب.

## 7. قواعد استنباطية من قراءة المشروع (Project-derived Rules)

بعد قراءة بنية المشروع والملفات التنفيذية، نوصي بإضافة قواعد عملية تكمل القواعد العامة، وتستجيب لمخاطر فعلية لوحظت في المستودع.

- **G11 — قاعدة إلزامية الاستخدام الفوري (Immediate Utility Mandate):**

  - نص القاعدة: لا تُدرج تبعية في `requirements.txt` إلا إذا كانت مستخدمة فعليًا في الكود الموجود ضمن `src/` أو في سكريبتات التشغيل المجمّعة في `scripts/`.
  - كيفية التطبيق: أضِف خطوة CI تُشغّل فحصًا بسيطًا لاكتشاف الحزم المدرجة وغير المستخدمة (مثلاً: `pipreqs` لمقارنة الاستيرادات مع `requirements.txt` أو سكربت مخصص). أي تبعية غير مستخدمة تُفتح لها Issue أو تُزال.

- **G12 — قاعدة مركزية التكوين (Centralized Configuration Mandate):**

  - نص القاعدة: جميع القيم القابلة للتغيير (أرقام المنافذ، عناوين خدمات مثل `OLLAMA_URL`, معرفات النماذج) يجب أن تُعرّف في مصدرٍ واحدٍ (مثل `.env` أو `config/` أو `config/paths.yaml`) وتُستدعى منه بقية الملفات.
  - ملاحظة تطبيقية: لاحظنا تكرارًا لرقم المنفذ `11434` ووجود متغيرات بيئة متشابهة (`OLLAMA_URL` مقابل `OLLAMA_API_BASE_URL`). توحيد الأسماء يمنع تشتت التكوين. أضف فحصًا سريعًا في CI أو PR template يطلب التحقق من أي تغييرات على القيم الأساسية.

- **G13 — توحيد التخزين حسب نوع النموذج (Storage Uniformity by Type):**

  - نص القاعدة: قسّم مجلد `models/` إلى مسارات فرعية منطقية حسب النوع أو المنصة (مثلاً `models/gguf/`, `models/onnx/`, `models/torch/`). ضع ملف `models/README.md` يشرح تنسيق الأسماء المتوقّع ومواضع تحميل النماذج.
  - سبب الفائدة: يسهل إدارة النماذج، يدعم قواعد M2 (البقاء على بدائل مستقرة)، ويجعل من السهل كتابة سكربتات تحميل أو نقل نماذج بحسب النوع.

- **G14 — قاعدة رقمنة التقييم والاختيار والتجريب (Digitize Evaluation, Selection & Experimentation):**

  - نص القاعدة: يجب رقمنة كل تجربة وتقييم اختباري مع سجلٍ موحدٍ يحتوي على: معرّف التجربة، وصف قصير، النسخ المستخدمة من البيانات (`data/clean` أو `data/raw` مع شناكات/IDs)، إعدادات التجربة (seed، hyperparams، نسخة النموذج)، مقاييس الأداء الأساسية، زمن التشغيل، ومكان تخزين المخرجات/النماذج (`experiments/` أو `new-project/ai-school/experiments/`).
  - كيفيّة التطبيق العملية:
    1. أنشئ سجلًا للتجارب بصيغة قابلة للقراءة والبحث (مثلاً `experiments/experiments_index.jsonl` أو `experiments/<experiment_id>/metadata.json`).
    2. كل تجربة تُنتج ملف `metrics.json` صغيرًا يحتوي على المقاييس الأساسية (accuracy, precision, recall, latency, cost-estimate) بالإضافة إلى حقل `decision` الذي يصف ما إذا كانت التجربة تُؤهل للانتقال (accept/reject/needs-more-data) وسبب القرار.
    3. خزّن النموذج الناتج في مسار منظّم تحت `models/` مع تسمية منطقية تشير إلى `experiment_id` و`type` (مثال: `models/gguf/ai-school-v1-experiment-20251125.gguf`).
    4. أضف سطرًا تلقائيًا في `docs/history.md` أو افتح Issue يربط `experiment_id` بنتيجة القرار، خصوصًا إذا قرر المسؤول اعتماد النموذج أو تغييره.
    5. عرّف معايير اختيارٍ مبدئية (مثلاً عتبة أداء، أو trade-off بين latency وaccuracy) تُستخدم آليًا أو شبه آليّة لاختيار المرشّحين للمرحلة التالية.
  - فائدة القاعدة: رقمنة التجارب تُقلّل الجهود اليدوية، تُسرّع اتخاذ القرارات المبنية على بيانات، وتُتيح مقارنة معيارية بين طُرُق أو نماذج مختلفة مع احتساب التكلفة/الفائدة.
  - إنفاذ القاعدة (Enforcement):
    - في متطلبات PR: عند تقديم PR الذي يضيف/يغيّر نموذجًا أو تجربة، اجبِر صاحب PR على تضمين `experiment_id` المرتبط، رابط إلى `experiments/` وملف `metrics.json` أو توضيح سبب الاستثناء.
    - في CI (اختياري): أضِف خطوة تحقق بسيطة في مسار الـCI تتأكد من وجود `metrics.json` بعد تشغيل مهمة smoke أو أن PR يحتوي على حقل `experiment_id` في وصفه إذا كان يتضمن تغييرات على النموذج.
  - أمثلة تطبيقية سريعة:
    - تشغيل تجربة موثقة ينتج `experiments/exp-0001/metadata.json` و`experiments/exp-0001/metrics.json` ونسخة نموذج في `models/`؛ يسجّل المسؤول النتيجة في `docs/history.md` ويحدّث README التجريبي.
    - عند مقارنة نموذجين، استخدم `experiments_index.jsonl` لاستخراج أفضل مرشح حسب `cost-estimate` و`accuracy` ثم احتفظ بالنتيجة كـ `decision: accept` أو `reject` في سجل التجربة.

تطبيق هذه القواعد يقلّل أخطاء الإجرائية (procedural errors) عند إدخال تبعيات أو نماذج جديدة، ويربط التغييرات بالوثائق (M6).

- **G15 — إلزامية تناسق التسمية (Naming Consistency Mandate):**

  - نص القاعدة: يجب توحيد أنماط التسمية عبر المستودع. نوصي باستخدام `snake_case` لملفات ومجلدات الكود داخل `src/` و`tests/` (مثال: `data_loader.py`, `preprocess_data.py`)؛ واستخدام `kebab-case` لملفات التوثيق والتهيئة في `docs/` و`config/` (مثال: `project-guide.md`, `docker-compose.override.yml`).
  - كيفيّة التطبيق:
    1. عند إنشاء ملف جديد حرِص على اختيار النمط المناسب حسب المجلد (قائمة مرجعية: `src/` → `snake_case`, `docs/` و`config/` → `kebab-case`).
    2. في PR وصفيّ، أضِف سطرًا يذكر أن تسمية الملف تلتزم بـG15 أو سبب استثناء مقنّن.
    3. يمكنك استخدام سكربت فحص بسيط (مخطط) في CI لفحص توافق أسماء الملفات مع الأنماط المتفق عليها (اختياري).
  - لماذا: تناسق التسمية يحسّن قابلية القراءة، يجعل أدوات البحث والفرز أكثر موثوقية، ويقلّل الأخطاء الناتجة عن إسقاط المسارات الخاطئة.

### I. شرح وتفصيل القواعد الناقصة

تحت هذا القسم نعرض الشرح التفصيليوالنصوص التعريفية للقواعد الخمس المتبقية كما طُلب، لتضمينها بشكل واضح في التوثيق المركزي.

#### 1. M5 — إلزامية حماية الملفات الجوهرية (Core Files Protection)

- الغاية: ضمان **الثبات (Stability)** للمشروع ومنع **الحذف العرضي أو التعديل غير الموثق** للملفات التي تُشغّل البنية التحتية وتوثّق الميثاق (القواعد).
- الوصف الإلزامي: تصنيف وحماية الملفات الأساسية التي لا يجوز حذفها أو تعديلها إلا بموافقة صريحة وفي إطار عملية PR مُوثقة.
- أمثلة على الملفات: `STANDARDS.md`، `docs/RULES_SUMMARY.md`، ملفات CI/CD (`ci-*.yml`)، وملفات بناء البيئة (`Dockerfile`).

#### 2. M7 — إلزامية رقمنة وتقييس القرارات (Digitalized Standardization of Decisions)

- الغاية: فرض **الموضوعية وقابلية التدقيق (Auditability)** على القرارات الجوهرية، وتجنب اتخاذ القرارات بناءً على الانطباعات الشخصية.
- الوصف الإلزامي: يجب أن تكون جميع القرارات الجوهرية (اختيار نموذج، بنية تحتية، تعديل استراتيجي) مُدعمة بـ **بيانات مُقاسة ومُرقمَنة** (مثل نتائج اختبارات CI، سجلات التجارب، أو مقاييس الأداء).
- آلية التطبيق: يتم تطبيقها عبر إنشاء قوالب (`metrics.json`, `metadata.json`) في مجلد `experiments/` لتسجيل الدليل الكمّي.

#### 3. M8 — التزام التحديث الدوري (Periodic Update Commitment)

- الغاية: ضمان **الصحة (Health)** للمشروع ومنع **انحراف التوثيق (Documentation Drift)** حيث تصبح الوثائق قديمة ولا تعكس حالة الكود الحالية.
- الوصف الإلزامي: يجب مراجعة وتحديث الملفات التي تتغير تبعيتها أو تتأثر بالكود بشكل دوري (مثلاً شهريًا أو مع كل إصدار رئيسي). يشمل هذا الملفات الخارجية (مثل `requirements.txt`) والتوثيق الأساسي (`README.md`).

#### 4. M9 — حظر التسمية والاحتواء العابر للمشاريع (Cross-Project Naming and Containment Ban)

- الغاية: **منع تلوث نطاق العمل (Scope Contamination)** وتجنب خلط ملفات المشروع الأم بملفات المشاريع الفرعية.
- الوصف الإلزامي: يجب ألا تحمل الملفات الأساسية للمشروع الأم **أبداً** اسم أي مشروع فرعي داخلي. كما يُحظر نقل الملفات الأساسية إلى المجلدات الفرعية (مثل نقل ملف تكوين من الجذر إلى مجلد `ai-school/` دون مبرر).

#### 5. R5 — إلزامية الجودة الآلية (Automated Quality Mandate)

- الغاية: ضمان **الاتساق الآلي (Automated Consistency)** في الكود المكتوب بين جميع المساهمين، وتقليل الحاجة للمراجعة البشرية للتنسيق.
- الوصف الإلزامي: يجب أن تكون أدوات تنسيق الكود (مثل Black/Ruff) وإدارة التبعيات الآلية (مثل Dependabot/Pip-Compile) إلزامية ومُثبتة **بنسخ ثابتة** عبر خطافات `pre-commit` وCI.

---

هذه التعريفات هي النصوص الرسمية التي يُنصح بإدراجها في `docs/RULES_SUMMARY.md` (كموجز) و`docs/STANDARDS.md` (كمحتوى مفصّل)، مع ربط تنفيذها إلى `docs/OPERATIONAL_CHECKLIST.md` و`scripts/` حيث وُجدت أدوات تنفيذية.

## 6. تتبّع التغييرات وإضافة قواعد جديدة

- كل قاعدة جديدة أو تعديل في القواعد يجب أن يسجّل في `docs/history.md` مع وصف سبب التغيير، تاريخ القرار، والجهة التي اعتمدت التغيير.
- لاقتراح قاعدة جديدة: افتح Issue أو ارسل PR مع الملف المحدث `docs/history.md` و`docs/STANDARDS.md`، واطلب مراجعة من صاحب المشروع.
